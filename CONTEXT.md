# Nahel — Ubiquitous Language

Glossary of the domain model. Terms here are used exactly and consistently in code, workflows, docs, and conversation. Maintained via the domain-modeling discipline; sharpen a term the moment it wobbles.

## State

- **Work item** — the unit of intent: a typed, sized record (markdown + frontmatter) with a lifecycle. Types: `feature | bug | chore | plan | prototype | qa`. Work items form a hierarchy via `parent`: an epic is a work item with children; a task is a leaf. There is no separate epic/task record type.
- **Work item ID** — a stable, randomly generated short identifier, merge-safe across parallel worktrees. The slug/name is for humans; mirrors carry the pretty number (e.g. GitHub issue #). References always use the ID, never the slug.
- **Type** — what kind of work an item is; picks the workflow.
- **Status** — the coarse universal lifecycle every work item shares, regardless of type: `backlog | in-progress | blocked | in-review | done | dropped`. Queries, briefs, and mirrors only ever need this enum.
- **Phase** — the fine-grained, per-type position within an active run (e.g. bug: diagnosing → reproducing → fixing). Lives in hot state, not item frontmatter; owned by the workflow.
- **Actor** — who performed an event or mutation: `human` or `agent`, with an identifier (e.g. `jim`, `claude-code`, `codex`). Required on every journal event; consensus, digests, and claim/handback semantics depend on it.
- **Lane** — how much ceremony the work gets (`direct | epic-lite | full`); picked by verified scope, scales ceremony *within* a type.
- **Roadmap node** — the layer *above* work items (Phase 4): one record type (markdown + frontmatter, `nahel/roadmap/`) with `kind: product | feature | initiative`, forming a tree via `parent` — product intent → feature intent → the work items themselves, which are generation three and unchanged. The node's intent prose is its markdown body. A product node points at a permanent design doc and cross-references ADRs; a feature node carries its PRD path, the id of the epic work item it covers, and optionally the released node it continues (`predecessor`); an initiative links sideways into several feature nodes. **Reference direction is one-way and canonical: the node points at the work item, never the reverse** — nothing about that relationship is ever written onto an item record. A node carries **no status field**: every status it renders is derived. Per-kind structural rules are soft — an odd shape is a `nahel validate` warning, never a refused mutation.
- **Roadmap view** — the zooming read over that tree (`nahel roadmap [ref]`, Phase 4): with no ref it is the product level — one line per product node with the derived distribution of its features, then those features grouped by horizon with their derived columns; with a node's slug or id it zooms to that node — breadcrumb, its own fields and intent, its chart, its children, and, for a feature, the work items under its epic. Every rendering ends with the commands that carry the reader further down. A pure read: it derives, never writes, and refuses nothing but a ref that names no node.
- **Horizon** — when a roadmap node is meant to be worked: `now | next | later`. The only sequencing vocabulary the roadmap has — no rank, no score, no priority number is ever stored — and multiple parallel `now`s are the intended shape, never a defect.
- **Roadmap migration** — the one-time act that gives a store with work items but no roadmap its first one (Phase 4; `nahel/workflows/migrate-roadmap.md`): every roadmap-shaped **top-level** item the store carries at migration time becomes a feature node under one product node. The candidate line is drawn by PARENT and by one status: an item with **no parent** at any status but `dropped` — `backlog`, `in-progress`, `blocked`, `in-review` and **`done`** alike. Done is in because the roadmap's job is built / in-flight / planned rather than planned alone (a delivered product would otherwise migrate to an empty roadmap), and a done feature's node says `built` without help — the column derives it from the epic. The rule is **coverage, not a count** — the set is enumerated from the store itself (`nahel status`), never from a document, which is only a snapshot of the day it was written. Capabilities that shipped **before this store existed** are out of scope entirely: they carry no work item, so a node for one would render `planned` while claiming shipped history, and bringing them in is a separately-designed **historical import**, not a migration judgment. What counts as roadmap-shaped is a **judgment**, and the CLI never judges (HC1), so the call is the migrating agent's — which is why the selected set is journaled FIRST: one `roadmap.migration-selected` event, payload `included` (every id that gets a node) and `excluded` (every **near-miss** as `{id, reason}`), written **before the first node** is created. Both lists are read **strictly** — every entry a work-item id, no id twice on either list, no id on both, every reason non-blank — and a malformed or *absent* list is an error rather than a set quietly read as smaller than it was: a migration that ruled nothing out says so with an empty list, and silence is not that statement. What proves the call was made rather than reconstructed from whatever nodes happen to exist afterwards is one comparison, not rendered order: the selection event's `ts` **strictly earlier** than every `roadmap.node-created` `ts`. A **same-second** tie fails the migration exactly as a late set does — segments are per-invocation and second-precision, so a tie breaks on random event id and renders in the right order about half the time. An open-extension type recorded through `nahel log`, never self-recorded by a command. Migration writes **node records only**: the node names the item it covers through `epic`, that reference stays one-way, and `git diff` over `nahel/items/` is empty across the whole act. Every node a migration creates is **attributed** to its selection — `nahel roadmap node new ... --migration <selection-event-id>`, carried on the creation EVENT rather than the record — and `nahel validate`'s `roadmap.migration-audit` joins the two, reporting uncovered ids, invented coverage, duplicate nodes and a non-strict order as errors while ignoring unattributed nodes entirely. A selection with **no attributed node** earns one advisory warning and never an error: it is either a migration mid-flight or a **legacy** one made before attribution existed, and a finished legacy migration is history rather than a defect. Attribution to a **retired** attempt is refused by the verb and reported as an error when a merge lands one anyway — a live node whose attempt is superseded belongs to no migration anyone audits.
- **Migration supersession** — how a failed migration attempt is retired (Phase 4, PR #26 follow-up C3): `nahel roadmap migration supersede <selection-event-id> --reason <why>`, a write-ahead sequence that journals `roadmap.migration-superseded` `{selection, reason, nodes}` and moves every attributed node record under `nahel/roadmap/failed/<selection-event-id>/`, where no list, view or check reads it (list scans keep only `*.md` at one level). A **correction, never a deletion**: the selection and the node-creation events stay exactly where they are, and `git revert` is the wrong tool — a git history is not the store's history. Refused when the attempt was already superseded, when it has no attributed record to move (a pre-attribution attempt cannot be retired this way), or when a node or map outside the attempt still points at one of its records — the blockers are named and nothing is written. After a supersession there is **no active selection**, and exactly one fresh one may follow. A retired record is absent ON PURPOSE, so `validate` never reports it as behind its creation event and `validate --repair` never writes it back.
- **Stage** — the single word a feature node stands at (Phase 4): `released | deployed | tested | built | in-flight | planned | unknown`, derived by **precedence, first match wins** — a covering `release.announced` reads `released`, else a covering `deploy.completed` reads `deployed`, else a covering `qa.sweep-completed` reads `tested`, else the dev rollup under the epic is itself the stage. Precedence, **not recency**: a deploy recorded after a release does not regress the feature to `deployed`. **Every word means the same thing: a well-formed fact said so.** A release must carry a nonblank `version`, `channel` and `announcement` — the same three keys `nahel roadmap archive` demands, one predicate, so a view can never promise a word the verb refuses; a deploy a nonblank `environment`; a sweep `failed` **0 exactly** (greater than zero, missing, non-numeric or negative are all not a pass). A fact missing any of that is not a fact the word can rest on, so the row falls through to the one below, down to the dev rollup — otherwise a workflow reaches the strongest word on the board by logging nothing at all. `validate` names each silent decline: `roadmap.sweep-failed-count`, `roadmap.release-incomplete`, `roadmap.deploy-incomplete`, each with the event id and the keys it lacks. The COLUMNS are untouched by all of it and still print what the store holds — `released ? <ts>`, `deployed ? <ts>`, `tested <ts> (4 failed)` — so a feature reads `built  qa=tested <ts> (4 failed)`: the column shows the fact, the stage says what it earned. A pure function of the store, so the same commit renders the same stage on any machine; there is **no stage field** to write, and the flags that would set one refuse by name.
- **Map** — the wayfinder chart of one roadmap node (Phase 4; markdown + frontmatter, `nahel/maps/`): a **Destination** (where the effort is going), **Notes** (the record's body), a **Decisions so far** index — one line per decision — the **fog** (*Not yet specified*: in-scope questions not yet sharp enough to ticket), and **Out of scope** (ruled beyond the destination; never graduates). One map per node. A map carries no status: what is settled is read from its decisions and its tickets. **The index sections are DERIVED and the record stores neither**: Decisions so far, and the Out-of-scope lines a `ticket close` earned, are composed at read time from the map's tickets, which already carry the decision and the ruling — a stored second copy made every resolution and every out-of-scope close rewrite the one record that every ticket on the map shares. Both order by the **journal event** that resolved or closed each ticket (`ts → seq → id`), never by the ticket's `updated`, which `distill` moves long afterwards. What the record does store is what was CHARTED with no ticket behind it: the fog, and the out-of-scope lines ruled before any ticket existed — ruling something beyond the destination needs no ticket, a decision always does.
- **Decision ticket** — one open question hanging off a map (`nahel/tickets/`), the question itself as its body, with `type: research | prototype | grilling | task` naming the surface that answers it. Four states — `open | claimed | resolved | closed` — and every transition is a named CLI verb, journaled. **Claim here is advisory assignment, NOT the intervention claim**: it records who is working the question so other sessions skip it, refuses only a second claim, and freezes nothing; release is permitted to any actor. Blocking edges run between siblings — tickets on the same map — and are advisory too: nothing anywhere refuses work because a blocker is open. Resolving journals the decision and distills an observation, so `nahel recall` finds it forever; the ticket's body may then be emptied by `distill` — through the CLI, never by editing the file. **Both terminal acts distil.** `resolve` takes an optional **`--rationale`** — multi-line prose, paragraphs kept, outer whitespace trimmed — which lives in the observation body and nowhere else: the one-liner says what was decided, and nothing else in the store says why. `close` distills its own observation under either disposition (`closed-<ticket-id>`, tagged `closed` plus the disposition, sourcing the close event, carrying the question, the ruling and the reason), because `distill` empties a closed ticket's body too and the question would otherwise be the one thing the store forgot. Closing states **which** disposition it is: *out of scope* (ruled beyond the destination — one line under that section, never graduates) or *invalidated* (another decision answered the question out of existence — the invalidating ref goes on the ticket, and it earns no Out-of-scope line, because an invalidated question was never beyond the destination). **Neither terminal verb writes the map**: the ticket records the decision (with its `resolution` event id) or the ruling (with its `closure` event id), and the map's sections are derived from exactly that.
- **Frontier** — the takeable edge (`nahel roadmap frontier [ref]`, Phase 4): everything that can start *now*, rather than what comes next in a plan. It spans **both** record kinds — a ticket-only frontier would answer *what can I decide* while going silent on *what can I build* — so eligibility is defined once per kind, because the two share no vocabulary. A **decision ticket** is takeable when its state is `open`, it has no claimant, and every blocking ticket has reached `resolved` or `closed`. A **work item** is takeable when its status is `backlog`, it is **not covered by an intervention claim** (its own `claimed_by`, or an **ancestor**'s — a claim covers the whole subtree), and every `depends_on` target has reached `done` or `dropped`. A reference no record carries counts as unsettled: it may arrive by a later merge, and `validate` reports the dangling edge. Both predicates are **read-only renderings**: nothing here refuses anything, an entry the list omits can still be started deliberately, and an empty section says *why* (blocked, claimed) rather than reading as an empty store. With a ref — a node slug or id, or a map id — it narrows to that node, but the predicates are still evaluated over the whole store, so a blocker or a claiming ancestor outside the node still holds an entry inside it back.
- **Anti-waterfall rule** — the doctrine the frontier is a view of (Phase 4): **blocking is advisory, everywhere**. No command anywhere refuses work because a blocker is open; an agent may deliberately start a blocked item, and doing so journals `item.started-with-open-blocker` — payload `from` and `blockers`, naming every dependency still short of `done`/`dropped` — so the choice is *visible* rather than prevented, and `nahel item update` says so out loud in the same breath. That type is the **write-ahead mutation event** for the transition: it REPLACES `item.updated` rather than following it, because advisory means *permit the start*, never *the provenance may disappear* — a second append is a note a kill can drop, and the blocked start it would leave behind is indistinguishable from an ordinary one, since the `item.updated` already matches disk. As the mutation event itself it inherits the one crash shape the store heals: the journal ahead of the record, rolled forward by `validate --repair` with the annotation intact. Build may start **before** a map is complete: a feature can carry an in-flight epic and an unfinished map at once, and no view or check calls that an error. Multiple **parallel** `now`s are correct, never warned about. A rule that refused would turn every advisory edge into a gate, which is the waterfall the roadmap layer exists to avoid.
- **Hot state** — `state.json` per run: current phase, statuses. Small, overwritten, machine-read. Lives at the run, not the work item.
- **Journal** — the append-only event record of what happened (`nahel log`), stored as JSONL segments — one segment per run (plus segments for non-run events) so parallel worktrees never merge-conflict. Reading merges segments by time. CLI enforces rotation; never edited, only appended.
- **Journal event** — one entry in the journal: unique ID (stable across rotation), timestamp, type, actor, optional run and work-item refs, payload. Event IDs are what provenance links point at. Mutation events are **write-ahead**: appended before the record change they describe, so the journal may run ahead of records after a crash but never lies about what happened.
- **Lifecycle event** — the two journal events that carry a feature past its own development (Phase 4): `deploy.completed` — payload `environment` (which environment it went to), `ref` (the deployed commit or tag), `shipped` (what went out) — and `release.announced` — payload `version`, `channel`, `announcement` (a pointer to the announcement). Open-extension types like the QA lane's, recorded by workflows with `nahel log <type> --item <id>` and never self-recorded by a command; like every logged observation they may carry no mutation payload key, so a lifecycle event can never masquerade as a record change. An event covers a feature node iff its `item` **resolves to** that node's epic item or to a descendant of it in the item `parent` tree — an epic id **no record carries** resolves to nothing, so it covers nothing, and no logged event can carry such a node past a development nobody can find (its dev status reads `unknown` and `validate` names the missing epic). The latest covering event of each type fills that column, and the three together collapse into the node's **Stage**.
- **Retraction** — `roadmap.column-retracted`, payload `event` (the id of the **Lifecycle event** or `qa.sweep-completed` being withdrawn) and `reason` (nonblank prose — **both halves required**, so a retraction missing either withdraws nothing and `validate` says so): the correction for a lifecycle fact recorded in error — a sweep summarised from the wrong run, a release announced early. Logged like the facts it corrects, and **not a deletion**: the journal stays append-only and the retracted line stays where it is; what changes is the derivation. The retracted event leaves column-winner computation and the winner is **recomputed from the survivors**, so retracting the latest sweep promotes the one before it rather than emptying the column. The **event id is the whole causal edge** — never the retraction's own timestamp (one logged before the fact it names still withdraws it) and never its `item` ref (coverage is the retracted fact's business). Only the three lifecycle facts may be named: a retraction of an item mutation, of another retraction, or of an id no event carries is structurally invalid — `validate` names it (`roadmap.retraction-malformed`, `roadmap.retraction-target-missing`, `roadmap.retraction-target-kind`) and the derivation ignores it. Retraction is **idempotent**, and there is **no un-retraction**: a mis-retraction is corrected by **re-logging the original fact**, which is a new event with a new id that nothing names. Under a human-owned product an agent's retraction raises the **awaiting-your-eyes** line and a human's clears it — it names no node, because it touches none. In **Standup** it is movement of its own, the `retracted` line beside the act it withdrew.
- **Observation** — one durable curated fact distilled from experience: one record per fact, with provenance = journal event IDs. Human-readable and editable in review. Searchable via `nahel recall`.
- **Knowledge layer** — the curated durable set: ADRs, this glossary, PRODUCT.md, ARCHITECTURE.md, observations, PRDs.
- **PRD** — a product requirements document: a knowledge document (`docs/prds/`) authored by a `plan` item and referenced by `feature` items via frontmatter path. Its draft→approved lifecycle lives on the owning work item, never in the PRD file.
- **PRD lifecycle** — a PRD is **live** — edited as the feature evolves — until that feature is archival-qualified, and **archived** after (Phase 4; `nahel roadmap archive <ref>`): the document moves to `docs/prds/archived/` with a stamped header carrying the released date, the epic and node it covered, the **journal pointer** (the id of the archival event) and the line that the **code and tests are the truth now**; the archival event names the release it rests on, so the pointer reads both ways. **Stage `released` and an archival-qualified release are different facts.** The **Stage** is a view of what the store holds and stays permissive: any covering `release.announced` reads `released`, and one recording nothing still renders `released ? <ts>`. Archival is not a view — it stamps a document closed forever on a header that cites the release — so it demands a release a reader can follow back: nonblank `version`, `channel` **and** `announcement`. Without all three the verb refuses, naming the release event and every missing key, and `validate` says `roadmap.release-incomplete` rather than `roadmap.prd-unarchived` — a warning must never name a command that then refuses. **No PRD is ever deleted**, and an archived one is **never** reopened and never edited — further work on a released feature is a **new node with a new PRD**, which may name the released one as its `--predecessor` for lineage; a node that is not released pointing into the archive is the `roadmap.closed-delta` warning. Archival is ONE act: every stored reference to the old path moves with the document — the feature node's link, the authoring plan item's `prd`, the epic's, and as a catch-all every other record holding it — so a dangling `prd` path afterwards is a bug, not a warning. **Product design docs are permanent**: the product node's design doc is updated **in place** in the same act (it gains the release's line), never archived — it states what the product *is*, where a PRD stated one delta. The archive holds **one file per delta** and an archived PRD is **never overwritten**: a basename is not unique across time, so a successor reusing the name its predecessor shipped under is refused outright, naming both paths for a human to rename — and repair unlinks a live PRD only into a destination carrying that act's own stamp. The whole sequence rides one write-ahead event, documents included, so a process killed at any boundary leaves the journal ahead and `nahel validate --repair` rolls it forward.
- **Brief / briefing** — the generated onboarding pack (`nahel brief`): everything a fresh agent needs to act correctly — goals, constraints, glossary, current state, recent activity — rendered from hot state + journal + knowledge. Answers *"what is this project and how do I act?"* It carries a capped **roadmap block** (Phase 4): at most **10** `now`-horizon nodes, one line each, in **horizon-entry order** — oldest first by the journaled act that set the node's *current* horizon (`ts` → `seq` → `id`), ties by slug — then a `+K more — nahel roadmap` line when more exist, then one summary line each for `next` and `later`. **13** lines at most, always: the block is deterministically ELIDED rather than truncated, because many parallel `now`s are the intended shape and a cap pretending to completeness would lie. A store with **no roadmap nodes** gets no block at all, not an empty frame.
- **Progress** — the rendered journal timeline (`nahel progress`): what happened and when. Answers *"what has been done?"* A view, **never canonical** — there is no hand-maintained progress file. Brief embeds a truncated version.
- **Standup** — the curated window over the journal (`nahel standup --since <7d|24h|ISO timestamp>`, Phase 4): what moved, what shipped, what parked, what got blocked in a time window, grouped by roadmap node and then by work item, every line naming the act it came from as `act=<event id>`. The words are read off the acts, never hand-set: `opened` (an item created), `moved` (a status transition), `blocked`, `parked` (dropped, or a run paused), `closed` (done), `tested` (a covering `qa.sweep-completed`), `shipped` (a covering `deploy.completed` or `release.announced`), `retracted` (a **Retraction** withdrawing one of those three — the original act's line stays exactly where it was, and this one follows it under the same work item, repeating what was withdrawn in its own words and naming the act it withdrew). An act that moved no status — a claim, an intent edit — is not movement; movement no node covers is grouped under *outside the roadmap* rather than dropped. Creates **zero new state**: no records, no events, no config, so the store is byte-identical after it runs. The window is computed from the injected clock alone, so `--since 7d` and the equivalent absolute timestamp render byte-identically.

## Governance

- **Constitution** — the human-owned core of PRODUCT.md: goal, domain facts, hard constraints, non-goals. Immutable without human sign-off in every mode.
- **Legislation** — delegable downstream decisions: priorities, PRD approvals, ADRs, architecture evolution.
- **Delegated governance** — a project mode where agent roles own legislation via cross-vendor consensus + append-only decisions + digests. Ships in slices: Phase 2 delivers the product slice only (`governance.product` — plan-item/PRD approval by cross-vendor consensus, no roles, no digest); role charters, architecture delegation, and `nahel digest` are Phase 5.
- **Agent-as-PO** — the `governance.product: agent` mode (Phase 4 roadmap layer): an agent owns product decisions on the roadmap outright, under its own authority, with no consensus step and no awaiting-your-eyes surface. Distinct from `delegated`, which keeps the cross-vendor consensus requirement. **Product-side only** — `agent` is not a legal `governance.architecture` value (that field stays `human | delegated`), which is why the two fields carry separate enums. Under `human` and `delegated`, agent-authored roadmap acts are recorded and never refused, but surface in `nahel brief` until a human-attributed roadmap act — or `nahel roadmap ack` — clears them.
- **Role** — an agent-neutral charter (product-owner, architect) grounded in the knowledge layer; reviews at gates.
- **Gate** — an artifact transition requiring a verdict (PRD `draft→approved`, epic plan sign-off, diff review). Roles review at gates, not continuously.
- **Digest** — rendered summary of delegated decisions for human audit (`nahel digest`). Audit, not approval.
- **Merge authority** — per-project config for who may merge a reviewed PR: `merge: human` (the default everywhere, including when the section is absent — the PR waits for a person) or `merge: on-approve` (reviewer sign-off merges). `on-approve` is the human's standing authorization, so it counts only when the journal shows a **human actor** made the config mutation that set it; an agent-set flag is inert, resolves back to `merge: human`, and `nahel validate` warns. Opt-in, used sparingly: small items, or changes QA testing covers well.
- **Consensus** — agreement between independent agents of different vendors (e.g. Claude proposes, Codex verifies) required for delegated legislation and AFK escape valves.

## Execution

- **Run** — one execution of a work item through its lane: a first-class record with its own ID, work-item ref, actor, phase, and lifecycle. An item may have many runs (attempt 1, attempt 2, resumed…); journal events reference the run. Hot state and `pause` target the run.
- **Run contract** — per-repo declaration of how to launch, seed, and test the app. Prerequisite for autonomy; checked by `nahel doctor`.
- **Verify-by-driving** — the invariant that an AFK run exercises the changed flow in the running app before its draft PR opens.
- **Ratchet** — QA discipline: agentic exploratory judgment is spent once per flow, then captured as deterministic e2e tests that run forever.
- **Investigation** — a bug's durable diagnosis document: symptoms, repro status, hypotheses tested, root cause.
- **Repro waiver** — the logged, surfaced exception to "failing repro test before fix"; valid only when the investigation shows failed repro attempts.
- **Pause / claim / handback** — first-class intervention operations. `pause` suspends a run. `claim` pins a work item at any level (one task or a whole epic) **and its entire subtree**: sets `claimed_by`, pauses active runs touching any covered item, and the CLI refuses agent mutations on claimed items — a guardrail against cooperating-but-fallible agents, with the journal making any bypass auditable. `handback` clears the claim and journals the human's changes; the agent resumes from the journaled delta.
- **Parked** — a decision routed to `human-review-needed` without blocking the run.

- **Responsibility** — a kind of judgment a project needs done: `architecture | implementation | review`. The unit routing maps to an executor; orthogonal to work-item type (one item exercises several responsibilities).
- **Routing map** — the committed config mapping each responsibility to a preferred executor (agent CLI and/or model), plus a default. Advisory to interactive sessions via the brief; enforced by autonomous dispatch.
- **Dispatch** — the deterministic act of launching a routed executor (`nahel dispatch <responsibility> --item <id> -- <task>`): resolve the route, compose the agent CLI's invocation (binary, model flag, `NAHEL_ACTOR`, an orientation preamble pointing at the brief), spawn it, record the run. Always item-scoped: every dispatch belongs to a work item, because the run it opens is how the work is attributed. Mechanics only — what to dispatch, when, and whether to stop are the host agent's judgment (ADR-0016).

## Interfaces

- **Canonical workflow** — the single agent-neutral procedure doc for a task (`workflows/*.md`); the only place logic lives.
- **Shim** — a generated per-agent entry point (slash command, prompt file) whose only job is "load canonical workflow X". Default prefix `/nd:`.
- **Mirror** — a one-way projection of local state into an external tracker (GitHub, Linear, …); humans read there, truth lives here. `external_refs` in frontmatter.
- **Inception** — the founding workflow: constitution, governance, glossary seed, run contract, first plan items. Tiers: `seed | standard | full`; every founding mines first and interviews second — brownfield mines the codebase, greenfield mines agent knowledge + the web (knowledge-first, Phase 2 F9); the interview is always confirm-and-correct. **Founding mode** — two interaction modes of the ONE workflow, captured up front and recorded as `config.founding`: `guided` (the human is grilled and corrects the drafts) and `hands-off` (`nahel init --hands-off "<paragraph>"` — the paragraph is the constitution's only human-signed content, verbatim; the agent's elaboration below it is unconfirmed knowledge, never constitutional text). Gates autonomy only.
- **Skill dependency** — a pinned external skill (`skills.yaml` + lockfile), `kind: markdown` or `kind: tool`.
- **Lab** — a real dogfood repo whose friction feeds Nahel's backlog.
- **Scaffolding** — the temporary ccpm + yolo tooling building Nahel until cutover (`nahel import --from-ccpm`).
