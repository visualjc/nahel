# Investigation — install-shim-dir-eisdir-on-prune (`33b2j3kq`)

## Symptoms

`nahel install --agent <x>` crashes with an unhandled `EISDIR` when the
generator-owned shim directory contains a **directory** whose name ends in
`.md` (e.g. a stray `notes.md/` folder). The whole install aborts — no
shims are written or pruned past the crash point.

## Repro status

Reproduced deterministically (see the "prunes around a directory named
*.md" test in `tests/commands/install.test.ts`): seed the shim dir with a
directory `junk.md/`, run install → unhandled `EISDIR: illegal operation
on a directory, unlink` (macOS; `EPERM`/`EISDIR` on Linux), exit via crash
rather than the command's error path.

## Hypotheses tested

1. **`listMarkdownDocs` returns directory entries** — CONFIRMED.
   `src/store/layout.ts` (`listMarkdownDocs`) uses bare `readdir(dir)` and
   filters only on the `.md` name suffix; entry type is never checked. The
   install prune loop (`src/commands/install.ts`) then calls
   `removeFile` → `unlink` on the entry. `removeFile` deliberately swallows
   only `ENOENT`/`ENOTDIR`; `EISDIR` (and Linux's `EPERM` for unlink-on-dir)
   propagates and crashes the command.

2. **`removeFile` should swallow `EISDIR` too** — REJECTED as the fix:
   swallowing would silently leave junk in a directory whose contract is
   "mirrors the workflow set exactly," and would also mask real bugs at
   `removeFile`'s other call sites. The list function is the liar here:
   a directory is not a markdown doc.

## Root cause

`listMarkdownDocs` classifies entries by name suffix alone, so a directory
named `*.md` flows into file-only code paths; the install prune loop
unlinks whatever it is given, and `unlink(2)` on a directory raises
`EISDIR`, which nothing handles.

## Fix

`listMarkdownDocs` reads with `withFileTypes: true` and excludes
directory entries (symlinks still pass — `unlink` handles them, and the
workflow-scan path already warns-and-skips anything unreadable as a doc).
The prune loop is unchanged: a `*.md` directory in the shim dir is simply
no longer a doc, so install completes around it and leaves it in place.
Deleting directories stays outside the store's deliberately file-scoped
delete primitive (`removeFile`), and recursively deleting user-created
content the generator never wrote would be worse than tolerating it.
